MIGRATION GUIDELeaguE INC. 社内用

クライアント自己管理への移管
対応手順書

クライアントが「ページを自社で管理したい」と希望された場合の、LeaguE側の対応手順です。LeaguEが行うのは「正しく動く状態のファイル一式をZIPにまとめて、クライアントへ送付する」ところまでです。GitHubアカウントやリポジトリの作成はLeaguEでは行いません。そこから先、GitHubアカウントの用意も含め、実際にどう公開するか（3パターン）はクライアント側ですべて選んで実施していただきます。クライアントへの依頼内容は、別紙の「クライアント依頼手順書」を送付してください。フェーズ2・4は、hp-enリポジトリに用意した専用スキル（Claude Codeのプロジェクトスキル）で実行します。手作業でのコピー・パス書き換えは行いません。

現状 hp-en共有リポジトリ内の1ファイル LeaguEの担当範囲 ファイル一式をZIPにして送付するまで フェーズ2・4 hp-enのプロジェクトスキルで自動実行 移管後 GitHubアカウント作成〜公開方法の選択・実施はすべてクライアント

前提知識：なぜローカルでファイルをまとめる作業が必要か

現在、全クライアントのページは hp-en という1つの共有リポジトリの中に、sites/carrirare.html のように1ファイルずつ同居しており、画像も共有の images/・logos/ フォルダを他クライアントと共用しています。このままではクライアントにファイルだけを個別に渡すことができないため（GitHubのアクセス権自体は渡さない方針のため、なおさら）、対象クライアントの分だけを抜き出し、単体で正しく動く1つのフォルダにまとめる作業が、どのパターンを選ばれる場合でも共通の下準備として必ず必要になります（フェーズ2）。この作業はLeaguE担当者のPC上でローカルに行うだけで完結し、GitHub上に新しいリポジトリを作る必要はありません。

LeaguEの作業は、ZIPを渡すところで完全に終わります。 以前の案では「独自ドメインだけ希望」「GitHubごと移管」で対応が分岐し、さらにその後の案でも「LeaguE名義でリポジトリを作って渡す」工程がありましたが、この見直しで、LeaguE名義のGitHubリポジトリは一切作成しません。LeaguEは常に「ローカルでファイル一式を整える→ZIPにしてクライアントへ送付する」だけを行い、GitHubアカウントの作成から公開方法の選択・設定まで、そこから先はすべてクライアント側の判断・実施に委ねます。これにより、クライアントとの往復のやり取りやLeaguE側の作業を最小限に抑えられます。

フェーズ2（ファイル書き出し）とフェーズ4（旧URLの案内ページ設置）は、手作業をやめてhp-enリポジトリのプロジェクトスキルで実行します。 Claude Codeで hp-en を開き、対象クライアントのスラッグ（例：ykn）を指定してスキルを呼び出すだけで、コピー・パス書き換え・整合性チェック・ZIP化までを一度に行います。手順の内容自体は変わりませんが、実行者が手でファイルを操作しないため、パスの向きを間違える・他クライアントのファイルを混ぜるといった従来のミスが起きにくくなっています。

移管後にクライアントが選べる3パターン

いずれも、LeaguE がフェーズ3で送付するZIP（index.html＋images/＋logos/）の中身をそのまま使えます。相対パスの静的HTMLだけで作られているため、特別な変換をしなくても3パターンすべてに対応できます。

パターンURLの例クライアントが追加で行うこと費用
1：github.ioで公開username.github.io/repo名/GitHub Pagesを有効にするだけ無料
2：GitHubに独自ドメイン設定クライアント所有ドメインGitHub Pagesを有効化＋DNS設定ドメイン代のみ
3：他社サーバーへ移設クライアント所有ドメインファイルをサーバーへアップロード＋DNS設定ドメイン代＋サーバー代

この3パターンの具体的な手順は、クライアント依頼手順書に記載済みです。LeaguEが代行する工程ではありませんが、クライアントから問い合わせがあった場合に内容を把握しておけるよう、依頼手順書の内容にも目を通しておいてください。

01

ヒアリング：送付方法と希望を確認する

目安 5分〜（クライアントからの返信待ちあり）

  1. 「クライアント依頼手順書」を送付する

    別紙の依頼手順書をクライアントに送ります。この時点でGitHubアカウントの有無やユーザー名を確認する必要はありません（ZIPで渡すだけなので、LeaguE側は相手のアカウント情報を一切必要としません）。ZIPの送付先メールアドレスの確認と、移管後にどのパターンで公開したいかの希望（決まっていなくても可）を回答してもらえば十分です。

  2. 回答が揃ったらフェーズ2へ進む

    送付先が確認できたら、次のフェーズに進みます。

この時点でできていること

ZIPの送付先と、（分かれば）希望する公開パターンが確認できている状態。

02

ローカルにファイル一式を書き出す（handoff-packageスキルで実行）

目安 3〜5分（+ 目視確認）

  1. Claude Codeでhp-enリポジトリを開き、スキルを呼び出す

    対象クライアントのファイル名（sites/配下、例：ykn.html）を指定して、/handoff-packageスキルを実行します。sites/プレフィックスや.html拡張子は付けても付けなくても構いません。

    Claude Codeでの実行例SLASH COMMAND
    /handoff-package ykn.html

  2. スキルが自動で行う内容

    手作業でのコピー・置換は行わず、以下をスキルが一度に実行します。

    • ~/Downloads/ykn-handoff（既定の出力先。第2引数で変更可）に作業フォルダを作成
    • sites/ykn.html の中身を、作業フォルダ直下に index.html として保存
    • index.htmlが実際に参照している ../images/...・../logos/... のローカル画像だけを特定し、作業フォルダの images/・logos/ にコピー（Drive由来など絶対URLの画像はコピー対象外）
    • index.html内の ../images/・../logos/ を images/・logos/ に一括置換（書き出し後はindex.htmlが直下に来るため、../を外す向きの補正）
    • 置換後、画像参照ごとに対応ファイルが実在するかを再スキャンして確認（欠けていればレポート）
    • 作業フォルダを ZIP に圧縮

  3. スキルが促す目視確認を必ず行う

    スキルは可能であれば作業フォルダのindex.htmlを既定のブラウザで自動的に開きます。ここは自動化できない工程のため、画像・レイアウトが元のページと同じように表示されているか、必ず担当者の目で確認してください。崩れていると、渡した後にクライアント側で切り分けるのが難しくなります。

  4. 完成したZIPを確認する

    スキルの実行結果として、ZIPのフルパス、コピーした画像/ロゴの一覧、壊れていた参照（あれば）が報告されます。これがフェーズ3でクライアントに送付するファイルになります。

スキルが自動でガードしている点

以前の不具合（sites/フォルダ内では逆に../images/...が必要だった件）の逆方向のパス補正、および他クライアントのファイル混入（images/・logos/を丸ごとコピーせず、実際に参照されているファイルだけをコピーする）は、スキルの手順に組み込まれているため手動で気をつける必要はありません。ただし、スキルが「壊れた参照」を報告した場合は、元のsites/配下のHTMLとimages/・logos/フォルダの状態を確認してください。

この時点でできていること

対象クライアントの分だけを含む、単体で正しく動くZIPファイルがローカルに用意できている状態（目視確認済み）。リポジトリ名の付け方（username.github.ioなど、URLをシンプルにしたい場合の設定）はクライアント自身がGitHub上で行うため、LeaguEが検討・準備する必要はありません（詳細はクライアント依頼手順書に記載済みです）。

03

クライアントへZIPを送付する

目安 10分

  1. ZIPをメールに添付して送付する

    フェーズ2で作成したZIPファイルを、クライアント担当者宛のメールに添付して送付します。ファイルサイズが大きくメールに添付できない場合は、社内で利用しているファイル転送サービスを使ってください。GitHubのアカウント作成や招待といったやり取りは一切不要です。

  2. 送付時に、使い方の案内を添える

    ZIPの中身（index.html・images/・logos/）の使い方は、別紙の「クライアント依頼手順書」にまとめてあります。メール本文でも、依頼手順書を参照するよう一言案内してください。

  3. クライアントに送付する

    ◯◯様 お待たせいたしました。ご依頼いただいておりましたホームページデータです。 ホームページのデータ一式をZIPファイルにまとめ、ギガファイル便にてお送りいたします。ご確認ください。 ＜＜ギガファイル便のURL＞＞ 今後の公開方法（3つの選択肢）につきましては、こちらの「ホームページの自己管理への移管に関するお願い」に手順をまとめておりますので、そちらをご参照のうえお進めください。 https://league-jp.github.io/hp-en/docs/client-domain-migration-request.html ご不明な点がございましたら、お気軽にご連絡ください。
この時点でできていること

ページのデータ一式がクライアントの手元に渡り、以後のGitHubアカウント準備・公開方法の選択・実施をすべてクライアント側で行える状態。LeaguE側の作業はここで一区切りです。

04

旧URLからのご案内・社内の後片付け（old-url-redirectスキルで実行）

目安 5分（+ 社内記録の更新）

  1. クライアントの新URL公開が完了してから実行する

    このフェーズは、クライアントが実際に新しいURLで公開を終えている前提で行います。まだ移管が完了していない、または新URLが未確定の場合はスキルを実行しないでください。

  2. Claude Codeでhp-enリポジトリを開き、スキルを呼び出す

    対象ページのファイル名と、移管後の新URLの2つを指定して、/old-url-redirectスキルを実行します。

    Claude Codeでの実行例SLASH COMMAND
    /old-url-redirect ykn.html https://ykn.example.com/

  3. スキルが自動で行う内容

    • sites/ykn.htmlの現状を確認し、既にリダイレクトページになっていないかチェック
    • 下記テンプレートの新しいURLをここにを実際の新URLに置き換え、3箇所すべてを揃えてsites/ykn.htmlを丸ごと上書き
    • 置き換え後の差分（git diff）を提示
    sites/（会社名）.html（旧URL側の中身がこれに置き換わる）HTML
    <!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta http-equiv="refresh" content="0; url=https://新しいURLをここに">
<link rel="canonical" href="https://新しいURLをここに">
<title>Moved</title>
</head>
<body>
<p>This page has moved to <a href="https://新しいURLをここに">https://新しいURLをここに</a>.</p>
</body>
</html>

  4. コミット・プッシュは必ず担当者が確認してから

    hp-enは複数クライアントの共有リポジトリであり、変更は実際の公開ページに影響するため、ファイルの上書き後、コミットするかどうかは必ず確認されます。コミットする場合も、プッシュは別途明示的な許可を得てから行われます（スキルが無断でpushすることはありません）。

  5. 社内の管理表・過去のSlack投稿・提案資料などのURL記載を確認する

    ここはコード変更を伴わないため、スキルは自動実行せずリマインドのみ行います。案件管理シートや過去のやり取りに旧URLが残っている場合は、可能な範囲で新URLに更新しておくと、後から見返したときの混乱を防げます。

この時点でできていること

旧URLにアクセスしても新しいページに迷わずたどり着ける状態。

05

最終確認・クライアントへの完了報告

目安 10分

  1. チェックリストで確認する

    • □ ZIPの中身をローカルで開き、画像・レイアウトが崩れなく表示されていた（フェーズ2のhandoff-package実行時に確認済み）
    • □ ZIPには対象クライアントのファイルだけが含まれている（他クライアントのファイルが混ざっていない）
    • □ ZIPをクライアントへ送付済み
    • □ 旧URLからも迷わず新しい移管先にたどり着ける（フェーズ4のold-url-redirect実行・コミット・プッシュ済み）
    • □ 社内の記録（案件管理表など）を更新済み

  2. クライアントに完了を報告する

    ◯◯様 お待たせいたしました。ご依頼いただいておりましたホームページデータの移管作業が完了いたしましたのでご報告いたします。 ホームページのデータ一式をZIPファイルにまとめ、本メールに添付してお送りいたしました。ご確認ください。 今後の公開方法（3つの選択肢）につきましては、別途お送りしております「ホームページの自己管理への移管に関するお願い」に手順をまとめておりますので、そちらをご参照のうえお進めください。ご不明な点がございましたら、お気軽にご連絡ください。
この時点でできていること

移管作業が完了し、クライアントへの報告も済んでいる状態。以降のGitHubアカウント準備・公開方法の選択・設定はすべてクライアント側で進めていただく状態。
